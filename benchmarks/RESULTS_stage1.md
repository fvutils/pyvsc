# Stage 1 overhead removal — results

Generated by `benchmarks/bench_stage1.py`, tracking
`doc/notes/vdc_stage1_impl_plan.md`. Back-end `dv-solve`, front-end `vdc`.
Absolute numbers are machine-dependent; the **ladder ratios** are the signal.

Command:

```
PYTHONPATH=src:benchmarks python benchmarks/bench_stage1.py --all
```

`--all` runs the throughput ladder, then re-executes with `VSC_PHASE_TIMERS=1`
for attribution — in a **separate process**, because the timers themselves cost
~100 ns per instrumented site, which is a few percent of the target budget.

Each Stage 1 step is behind a switch in `vsc.model.opt_flags`
(`VSC_S1_BULK_READBACK`, `VSC_S1_SKIP_COPYIN`, `VSC_S1_LAZY_WALKS`), all
defaulting to on, so the ladder can be re-derived on demand and a regression
pinned to one step.

## Finding: the plan-cache "knob" cliff (new, 2026-09-20)

Mutating a **non-rand dataclass field** between solves invalidates the Tier-A
plan cache, whether or not any constraint references that field:

| class | hook writes | solves/sec |
|---|---|---:|
| `H1` | a non-rand *field* (`self.seen = self.a`) | 11 982 |
| `H2` | a plain attribute (`self._seen = self.a`) | 91 195 |
| `H3` | nothing (no hook) | 85 530 |

**7.6×**, and the attribution shows why: on `knob`, `randinfo_build` runs on
every solve (1.00 calls/solve) and 73% of the budget is the rebuild it gates,
whereas on `hooks` neither appears at all.

The invalidation is *correct* but over-conservative. The plan's freshness
signature snapshots every non-used-rand field in `bound_m`; only fields a
constraint actually reads can change the solution. `seen` is read by nothing.

This is tracked as **S1.7** in the plan. It shares its analysis with S1.3 —
"non-rand fields referenced by a constraint" is precisely S1.3's copy-in set.

It also matters beyond benchmarks: "mutate a non-rand field, re-randomize" is
the config/knob pattern, and it is one of the lifecycle dimensions the parent
plan (`vdc_value_representation_plan.md` §5) says a representation must be
measured on.
