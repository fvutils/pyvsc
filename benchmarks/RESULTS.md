# Cross-frontend × cross-backend benchmark — results

Generated by `benchmarks/bench_frontends.py`. The benchmark answers two questions:
**why move backends** and **why move frontends**. Absolute numbers are
machine/run-dependent; the **ratios** are the durable signal. Representative run:
`PYTHONPATH=src python benchmarks/bench_frontends.py 500` (2026-06-17, post Phase-G +
soft + BV-SAT engine work).

- **Frontends:** `classic` (`@vsc.randobj`), `dc` (dataclass `vdc`).
- **Backends:** `dv-solve` (native + BV-SAT), `boolector` (external).
- **Workloads:** `simple`, `alu` (`inside`-heavy, 32-bit), `array8`, `wide64`
  (two 64-bit), `dist`, `nested` (two sub-objects).
- Classes are defined **once**; only object construction/solving is timed.

> **Update (2026-06-17):** dv-solve now **wins every workload** including `alu` and
> `wide64`, which the prior (2026-06-14) run reported boolector winning. Phase G
> (native unsigned-64 + multi-range `inside`), the soft-constraint engine work, and
> the BV-SAT buildout closed those buckets. Back-end geo-mean moved **4.3× → 20.8×**;
> the per-instance front-end win moved **3.2× → 7.3×** (with the wide/`inside` solves
> now fast, the dataclass build-elimination shows on those workloads too).

---

## Why move FRONT-ENDS?

The classic front-end re-elaborates the model on **every instance**
(per-instance `build_model()` — a `dir()` scan + constraint re-build). The dataclass
front-end elaborates structure **once per type** and reuses it. So the front-end
matters exactly when you **create many objects** — the realistic generator / UVM
sequence-item pattern (make item, randomize, send, discard, repeat).

**A. Per-instance** — construct a fresh object + randomize once (dc/dv-solve solves/sec):

| workload | classic/dv-solve | dc/dv-solve | **dc speedup** |
|----------|----:|----:|:--:|
| nested   | 2 198 | 32 232 | **14.7×** |
| simple   | 4 251 | 44 280 | **10.4×** |
| wide64   | 4 189 | 39 430 | **9.4×** |
| alu      | 2 785 | 25 003 | **9.0×** |
| dist     | 3 895 | 31 224 | **8.0×** |
| array8   | 1 407 |  2 019 | 1.4× |

geo-mean (per-instance, dv-solve): **dc 7.3× classic** (boolector 1.2×, where the
slow external solve still dominates the total).

> **What unlocks this: per-type translation caching.** The dataclass constraint
> model is *type-stable*, so the solve model is built **once per type** and shared
> across all instances (rebinding values per call). Because the root model *object*
> is then shared, the Randomizer's Tier-A plan cache (VariableBoundVisitor +
> RandInfoBuilder) and the dv-solve compiled-problem cache **hit for every
> instance**, not just for repeated randomize() of one object — the per-instance
> passes that a profile showed dominating the create-many path are skipped. The win
> is now broad: with dv-solve solving the wide/`inside` workloads natively (Phase G),
> `alu`/`wide64` also see ~9× from build-elimination, where they were ~1.1× when the
> external solve dominated.

**B. Reuse one object** — re-randomize the same object (warm plan cache):

| | classic/dv-solve | dc/dv-solve |
|--|----:|----:|
| simple | 59 853 | 57 436 |
| nested | 42 181 | 39 881 |

dc vs classic here = **0.97–1.00×** — identical, because both hit the same plan
cache.

**C. Construct-only** (no randomize): dc is **~1300×** faster — classic builds the
full model tree in `__init__`; dc construction is just dataclass field assignment
(the solve model is built lazily, once, on first randomize).

### Front-end takeaway

| usage pattern | move to dataclass? |
|---------------|--------------------|
| **create many objects** (generators, UVM items, layered sequences) | **Yes** — 8–15× faster across workloads (per-type translation cache + no per-instance build_model); 7.3× geo-mean |
| **reuse one object**, re-randomize in a loop | Neutral — pick the dataclass front-end for typing/IDE ergonomics, not speed |

The per-instance win is largest for **nested** types (classic rebuilds the composite
tree every instance) and for cheap-to-solve types (the eliminated build+translation
is a big fraction of the total). It shrinks toward 1× only when `foreach`
re-expansion disqualifies the plan cache (`array8`). The dataclass front-end is
**never slower**.

---

## Why move BACK-ENDS?

The solver dominates total time. dv-solve now **wins every workload** (per-instance,
dataclass front-end):

| workload | dv-solve vs boolector |
|----------|----:|
| wide64 | **43×** |
| alu    | **34×** |
| simple | **30×** |
| nested | **23×** |
| dist   | **12×** |
| array8 |  **6.6×** |

geo-mean ≈ **20.8×** toward dv-solve. The former regressions are closed:
`wide64` (0.3× → 43×) by Phase-G native unsigned-64, and `alu` (0.6× → 34×) by
Phase-G native multi-range `inside`. The per-type cache compounds the win on
cheap-solve cases by removing the pyvsc-side overhead that capped throughput.

### Back-end takeaway

dv-solve is now the default choice across these workloads (6–43×). boolector remains
available as the XCHECK oracle and a fallback for the few constructs dv-solve still
escalates (e.g. a relaxation-bearing `!=` soft, >255-bit fields). Pick boolector only
if a specific workload regresses under dv-solve and XCHECK confirms it.

# Cold-path size-sweep (native full-problem plan)

Harness `benchmarks/bench_coldpath.py`, tracking
`doc/notes/dv_solve_native_full_problem_plan.md`. **Size-dependent:** the
analysis-gating work does ~nothing on scalars and matters only on array-heavy /
wide problems. Do not read the scalar row as evidence either way.

## Stage 0 baseline — before gating (2026-07-09, dv-solve, scale=1)

### A. Cold throughput vs size — solves/sec (fresh object each solve)

| workload | N | baseline |
|---|---|---|
| scalar | 2000 | 28 345 |
| arr16  | 800  | 1 020 |
| arr128 | 120  | 137 |
| arr512 | 30   | 33 |
| wide64 | 200  | 161 |

### B. Phase attribution (arr128, cold) — `do_randomize` 2.598s / 120 solves

| phase | % of cold |
|---|---|
| native build+solve (incl. translate + ctypes) | 34.3% |
| **VBV (bound analysis)** | **24.5%** |
| RandInfoBuilder (partition) | 12.1% |
| array-expand | 10.5% |
| reuse-signature | 3.7% |
| dist-expand | 3.1% |
| native solve+readback (pure solve) | 3.0% |

Pure native SAT solve = 3% of cold; Python VBV bound analysis alone = 24.5%.
VBV is the Stage-1 target; RandInfoBuilder (12.1%) needs the native partitioner
(Stage 4).

## Stage 1 — declared-only bounds, Option A (default ON; kill-switch `VSC_DVSOLVE_DECLARED_ONLY=0`)

Landed. On the dv-solve path the post-expansion bound pass skips
range-inequality propagation for **narrow (≤32-bit)** fields (native re-derives +
samples them uniformly); it **keeps** `==` pins, `inside`/rangelist folds, and
**wide (>32-bit)** range propagators (the wide sampler needs the tight domain).

### Cold throughput — Option A (default) vs baseline (dv-solve, scale=1)

| workload | baseline | Option A | Δ |
|---|---|---|---|
| arr16  | 1 020 | 1 234 | +21% |
| arr128 | 137   | 165   | **+20%** |
| arr512 | 33    | 39    | +18% |
| wide64 | 161   | 192   | +19% |
| scalar | 28 345 | ~neutral | (within noise) |

VBV phase share on arr128: 24.5% → **13.6%** (residual = phase-0 + the phase-1
classification walk, which must run to know op/target-width; the ~44%-of-VBV
fixpoint savings land). Full `ve/unit` (529) + `ve/unit_dc` (313) pass with the
gate on and off. Guard: `ve/unit/test_dvsolve_declared_only.py`.

### Rejected: blanket declared-only (all propagation skipped)

Faster (arr128 +27%) but regresses 8 tests — wide `==`/range correctness,
contiguous rangelist folds, and wide-field sampler fairness. Not shipped.
The extra ~4–7% (skipping the phase-1 walk too) needs native-side work
(Option B): wide-literal translation, always-emit membership, native sampler
domain-tightening.

## Stage 2 — native free-var assignment: REFUTED (measured regression)

Routing unconstrained fields through a native solve is slower than the Python
`randint` loop in every scenario (64× unconstrained u32):

| approach | time (3000 × 64) | vs Python |
|---|---|---|
| Python `randint` loop (current) | 0.062s | — |
| native batch (build+compile+solve/call) | 0.256s | 4.0× slower |
| native ctx-reuse (compile once) | 0.075s | 1.22× slower |

Constraint-free fields have nothing to amortize the native build/ctypes crossing
against. Not shipped standalone — free-var assignment only pays when folded into
an already-running whole-problem solve (Stage 3/4).

## Stage 3 — whole-problem merged solve: SCOPED / PROTOTYPED (strong win)

arr128 is split into **128 independent RandSets** (one per element), each with its
own native crossing. Merging them into one solve (prototype on captured
`(ri, bound_m)`):

| path | per-RandSet (128×) | merged (1×) | speedup |
|---|---|---|---|
| cold solve (build+compile+solve+readback) | 428/s | 612/s | **1.43×** |
| warm solve (reset+solve, cached) | 4 407/s | 11 388/s | **2.58×** |

Correctness/distribution preserved (0/12800 out-of-range, mean 126.9 over [3,249]).
Safe because RandInfoBuilder emits maximal *independent* components (block-diagonal
merge, no coupling). Single-partition workloads unaffected. Recommended landing:
merge only *plain* partitions (≤64-bit, no dist/order/soft/wide), re-home the reuse
cache to one merged plan, fall back per-RandSet on UNSAT for attribution. Est.
+15–20% cold end-to-end on multi-partition workloads; larger on warm/reuse loops.

## Boundary investigation → array plan-cache reuse: LANDED (6–7× on arrays)

The dominant cost for array/`foreach` workloads was per-randomize *reconstruction*,
not the solve (arr128: native solve 0.04 ms vs randomize() 6.1 ms). The
compiled-problem cache missed entirely for arrays because `foreach` expansion
rebuilds fresh constraint objects every call (`id(c)`-keyed signature never matched)
— re-randomizing the same object rebuilt all 128 partitions every time.

Fix: extend the Tier-A plan cache to fixed-size array models
(`VSC_DVSOLVE_ARRAY_PLAN_CACHE`, default on) with three correctness guards
(element-count freshness, pre-expansion source rangelist/dist snapshot,
rollback-fragile-expansion exclusion). Regression: `test_dvsolve_array_plan_cache.py`.

### Cold throughput — array cache ON (default) vs OFF (dv-solve, create-many)

| workload | OFF | ON | speedup |
|---|---|---|---|
| arr16  | 1 241 | 7 790 | **6.3×** |
| arr128 | 164   | 1 132 | **6.9×** |
| arr512 | 39    | 244   | **6.3×** |
| scalar | 37 010 | ~31 000 | unchanged (noise) |
| wide64 | 193   | 190   | unchanged |

Warm repeat-randomize of one object (arr128): 6.1 ms → 0.82 ms (~7.4×),
builds/randomize 128 → 0.

## Whole-problem merged solve: LANDED (another 3–3.7× on top)

After the array cache, the warm path still ran the per-RandSet solve loop 128×.
Merging all independent RandSets into one native solve (reusing a ctx cached on
the plan; `VSC_DVSOLVE_MERGE`, default on) collapses that. Guards: fall back for
special RandSets (dist/order/soft/>64-bit/const-UNSAT), when XCHECK is on, and
above a var cap (`VSC_DVSOLVE_MERGE_MAX_VARS`=256 — a native super-linear cliff at
~256→384 vars).

### Cold throughput — merge ON vs OFF (array cache on in both; dv-solve, create-many)

| workload | merge OFF | merge ON | on-top | **vs original baseline** |
|---|---|---|---|---|
| arr16  | 7 534 | 19 172 | 2.5× | **19×** (from 1 020) |
| arr128 | 1 086 | 3 676  | 3.4× | **27×** (from 137) |
| arr512 | 237   | 240    | — (capped) | 7.3× (from 33) |
| scalar | 35 373 | 40 702 | — | unchanged |
| wide64 | 177   | 268    | — | unchanged |

Warm repeat-randomize (arr128): 0.82 ms → **0.23 ms** (~3.6× on top; ~27× vs the
6.1 ms baseline). Full `ve/unit` (542) + `ve/unit_dc` (313) green.
